# ForgeCode 十题评测深入审计与离线测试

审计对象：2026-09-15，GPT-5.6 Luna，并发 2，Terminal-Bench 2.0 固定十题。官方结果 4/10，13:33–15:24。本报告审计实际执行版本、原始事件、官方验证结果与现有代码；本轮未重新调用模型、未运行新一轮收费评测、未修改生产代码。

## 结论

ForgeCode 确实存在需要优先修复的问题，但不能将全部失败归为架构缺陷，也不能用公开 TB 2.1 全量成绩直接衡量本次十题的差距。

当前最主要的缺口是：模型用不充分的自测证明实现正确；交付前缺少独立于实现的反例检查；验收系统又会把合法检查误判成无效，产生大量难以利用的反馈。另有实际模型服务故障、任务预算耗尽和持久化开销。下一步应修复这些可证实的问题，暂不以全面重写、增加多代理或扩大上下文作为主要方案。

本次实现了证据持久化和完成报告，并不等于实现了可靠的正确性判断。649 项既有测试通过说明已覆盖行为未回归，不能证明未覆盖的不变量，也不能替代任务级正确性评测。

## 3. 已定位的共同问题

### 3.1 自测与实现使用相同假设，缺少反例

电路题的测试输入与查表实现完全重合；视频题放弃已观察到的窄范围，转而断言宽范围；蛋白题验证输出结构而没有与指定来源做逐组件完整比较；渲染题在包含参考程序的同一环境验证。这四类错误都能让测试“通过”，但没有证明任务要求成立。

应当按任务性质选择检查，而不是强制每个任务都生成通用 JSON 断言：算法问题需要实现未使用过的输入与独立结果；转换/组装需要来源精确性；构建需要从安装位置做最小真实使用；单文件交付需要依赖隔离。检查只能使用任务可见信息，不能读取官方隐藏测试来为候选定制答案。

### 3.2 要求登记与检查分类过度依赖字符串

`TaskManager._merge_acceptance` 用 `quote in source` 判断来源。真实用户原文只改变空格或换行也会被拒绝。模型随后继续使用自定义 clause ID，要求身份未正确绑定。

`verification_quality` 将未引用换行视为不安全 shell 链，合法 Python heredoc 会变成 unknown。命令拼接、AST 静态检查和真实端到端测试的分类也不稳健。不能把 unknown 进一步解释成“测试只掩盖失败”，更不能把不被分类器认可的 covers 报为没有覆盖声明。

修复方向：保留原文和位置，用规范化文本定位来源；区分声明的检查目的、进程执行事实和实际断言结果。对无法可靠解析的 shell，只标记出口语义未知，提供清晰的替代执行方式，如 `python -` 加 stdin；不要靠更多正则表达式充当语义证明。

### 3.3 历史检查未解决、检查器出错、真实行为失败混在一起

官方通过的 build-pov-ray 和 distribution-search 仍被报告为未满足内部验收；误写的检查器或过期检查会留下难以消除的义务。视频题也存在后续有效检查没有解除前序检查错误的问题。

需要独立表示 `check_definition_error`、`execution_error`、`behavior_failed`、`passed`、`stale/unknown`，并明确哪些新运行覆盖哪些旧定义。把所有失败永久保留为活动义务，会让反馈噪声淹没真实缺陷；丢弃所有旧失败又会允许弱化断言。应保留历史，按定义身份和覆盖关系计算当前视图。

### 3.4 完成声明降为 partial 后立即结束，缺少可用的诊断回合

避免反复拒绝 finish 的方向是对的；但本轮视频和渲染题在大量预算剩余时结束，具体不足未能成为下一次修复行动。单纯恢复旧的无限 finish 拒绝循环同样不可取。

建议增加独立的交付检查阶段：在提交前一次性汇总少量有证据支持的缺口，模型能继续修复，也能明确提交 partial。最终提交保持单次终止；自动化任务可以配置有限的修复回合，只有新证据或具体修复行动才能继续。验收报告本身不修改产物，也不把官方 reward 当作代理可见反馈。

### 3.5 运行健康与评测汇总存在分层盲区

CompCert 的三次 server_error 是实际模型故障，即使 Harbor 和进程监督器正常结束，也不能当作正常解题失败。需要同时统计调度层、代理终态、模型请求、验证器状态、官方 reward；不要通过从分母删除此题来提高原始通过率。原始 4/10 必须保留，另加分层解释。

推理档位也需要贯穿 CLI/env → benchmark wrapper → 子进程 → SDK → wire，并记录明确值或 unknown。只记录模型名不够证明跨 harness 的同条件比较。

## 4. 持久化成本的实测

生产 `SessionJournal._assert_append_head` 每次 append 都 read_text 整份先前日志，随后只校验最后一条记录。新增加的请求输入和实际 wire 快照让日志迅速增长；本轮十题按真实 JSONL 前缀长度计算，仅这一步累计重读约 **32.092 GB**，还未计入恢复和外置 artifact 读取。

离线对照保持同样的锁、UUID/sequence 一致性检查与 fsync，只把读取整个历史替换为从文件末尾分块读取最后一条记录。500 条、每条约 20 KB 的单次本机试验：

| 指标 | 生产实现 | 实验性尾部读取 |
|---|---:|---:|
| 最终日志大小 | 10.15 MB | 10.15 MB |
| 头校验累计读取量 | 2.532 GB | 32.63 MB |
| 总耗时 | 17.69 秒 | 8.42 秒 |
| 前 20 条中位追加耗时 | 13.57 ms | 13.20 ms |
| 后 20 条中位追加耗时 | 49.21 ms | 14.60 ms |
| 拒绝过期 writer | 是 | 是 |

这证明算法性放大和本机可测收益，不代表线上每题也能按相同比例缩短。真实轨迹中的 bookkeeping 相邻事件间隙合计，例如 MIPS 144.27 秒、POV-Ray 82.59 秒、JS 78.38 秒，包含执行器工作、调度与持久化，不能全部归因于磁盘。`model_seconds` 本身也含适配器和事件写入，不等于纯网络延迟。

建议先修复有界尾部读取并补竞争、崩溃、尾记录损坏与超大末条记录测试；其次把高频状态写入放在容器本地日志，按安全边界同步。关键副作用前后的持久化必须保留，不能直接取消 fsync 或异步丢弃记录来换速度。实验类只存在于诊断脚本，尚未替换生产实现。

复现：`.venv/Scripts/python.exe -m benchmark.analysis.probe_journal_cost --output docs/reviews/2026-09-15-journal-cost-probe.json`。详见 [测量数据](D:/projects/forgecode/docs/reviews/2026-09-15-journal-cost-probe.json)。

## 5. 修复优先级与验收方式

| 优先级 | 工作项 | 必须通过的验证 |
|---|---|---|
| P0 | 要求来源定位、检查分类和当前证据视图 | 合法原文空白变化可定位；正向 heredoc 不被误称掩盖失败；检查器修复能解除对应错误，降低断言阈值仍被拒绝 |
| P0 | 交付检查与反例机制 | 原有自测输入之外的失败可发现；样例矛盾能提示；精确组件截短可发现；干净目录暴露外部程序依赖 |
| P0 | 固定实际模型 profile、分层故障统计 | wire 中显式设置有效 reasoning；配置不支持时明确失败；server_error 在汇总中保留，不伪装正常完成 |
| P1 | 有界日志头校验与持久化分层 | 保留崩溃和并发保护；追加成本不再随完整历史线性上升；记录体积及写入耗时可观测 |
| P1 | 修复诊断测试揭示的预算/usage 等不变量 | 所有新增故障复现通过，再回归原有测试 |
| P2 | 完整中立消息 IR、助手并发、仓库地图 | 在同题/同 profile/同预算上单独消融；没有任务收益证据前不扩大默认复杂度 |

实施应按上述顺序做小范围改动，每一项使用对应的真实失败轨迹回放。不要同时改模型、prompt、工具、预算和 dataset 后将分数差归因于某一个模块。

后续付费验证先选覆盖独立机制的少量任务，使用冻结候选和预先声明的对照。最终仍回到同十题并发 2 的完整重复轮次。针对任务的公开说明构建检查是合理的；依据官方隐藏断言写特判不是有效改进。若要和其他 harness 对比，需要额外跑同一组任务及相同实际模型档位，而不是引用 2.1 榜单直接相减。

## 6. 本次新增测试与限制

本次新增的是离线审计与故障复现，不是新的模型解题样本。真实任务产物仅做数据读取和静态解析，没有执行从轨迹提取的任意程序。独立诊断套件的具体结果与未修复缺陷见 [运行时故障审计](D:/projects/forgecode/docs/reviews/2026-09-15-runtime-fault-audit.md)。

|---|---|---|---|
| 父级工具预算 | 根额度耗尽后子工具不能执行 | 仍执行一次 | 本轮没有助手，属于潜在缺陷 |
