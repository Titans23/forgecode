# Terminal-Bench 2 新增 20 题：实验分析与优化设计

## 结论

当前最值得做的是修复执行与交付边界，再调整验收闭环。已有证据支持对这些模块进行结构性改造，但不足以支持推倒 ForgeCode 的模型接入、事件日志和整个 Agent 内核重写。

本轮存在三类问题，不能用同一个“通过率低”解释：

1. **框架破坏有效交付或浪费预算。** 监督器正常退出时杀死后台服务；脱离进程组的后代使命令超时失效；全盘搜索先遍历整个目录树再过滤。
2. **模型得到的反馈没有可靠地反映正确性。** 自制检查重复实现中的假设、只匹配终端回显、把样本查表当成通用算法；另一些正确产物却被旧失败和验收登记问题长期阻塞。
3. **实验环境和评分口径存在混淆。** 镜像已下载仍不代表 verifier 的在线依赖可用；内部超时不能覆盖官方 reward；不同题集的 40% 与 45% 不能用来证明提升。

本次只补下载镜像、分析已有轨迹、执行短小的离线运行时复现实验。没有启动新模型评测，也没有修改产品执行逻辑或官方测试。

## 实验边界和真实结果

- 数据集：`terminal-bench/terminal-bench-2`，固定版本 `sha256:c6fc2e2382c1dbae99b2d5ecd2f4f4a60c3c01e0d84642d69b4afd92e99d078b`。
- 运行：`terminal-bench-2-unseen20-luna-c5-prepulled-20260915-193858/2026-09-15__19-39-04`。
- 模型：gpt-5.6-luna，经 Anthropic 兼容接口；未显式设置 reasoning，实际强度未知。
- 并发 5；配置上限为 120 模型请求、240 工具请求、1800 秒；每题实际内核期限还受题目时限约束。
- 20 题与此前 18 个历史题目无重叠，选择文件记录了固定种子、排除集和每题引用。

现有汇总器把超时且官方通过的 sqlite 排除出 eligible 集，输出 `final_pass_count=8`、`final_pass_rate=8/18`。**这不是官方原始成绩。** 建议原始 reward、verifier 是否有效、Agent 终止原因分别存储。仅剔除 verifier 未执行的 qemu，诊断值是 9/19；仍不能替换正式的 9/20，更不能将 qemu 假设成通过。

上一轮固定十题为 4/10。本轮换成二十个新题，45% 相对 40% 的差别混有题目难度、样本构成和采样因素，不构成代码提升的对照证据。

官方测试通过也不保证满足了题目全部语义，不能为校准内部状态而直接把这 9 题全改成 completed。应修复已证实的不适用约束和检查故障，保留真实缺口。

## 已复现的执行层问题

### 1. 正常退出时误清理任务要求保留的服务：P0

`benchmark/harbor/process_supervisor.py` 将自身设为 Linux subreaper，并在 finally 中无条件 SIGKILL 全部收养的后代。代码注释明确包括成功退出。这可以处理泄漏的编译器，却不符合“启动服务并保持后台运行”的任务合同。

gRPC 的真实轨迹：启动 `server.py` → 多次活体 RPC 调用 → 最终检查输出 `rpc_behavior=passed`、端口可达 → Agent 结束 → 官方测试连接拒绝。离线复现让监督器中的子程序启动本地服务并成功退出，监督器返回 0，但服务随即消失。被测源码 SHA256 与本轮冻结源码相同。

**设计：分离命令临时进程与任务交付进程的生命周期。** 命令进程归工具所有，超时或取消时清理；显式登记的任务服务归 trial 环境所有，存活至 verifier 完成，由容器 teardown 统一回收。正常结束移交服务所有权，失败/取消按服务策略处理。不能简单关闭所有清理，也不能假定所有后台进程都是泄漏。

新增后台会话接口应返回会话 ID、实际 PID/启动身份、日志位置和 readiness 状态；提供查询、等待、停止。对已有 nohup/daemonize 路径要明确处理兼容性：若评测环境在 Agent 结束后统一保留进程至 verifier，应只在隔离容器内实施并记录策略；生产宿主继续保留严格的所属进程回收边界。

**验收：** Agent 成功退出后服务仍可被独立进程调用；verifier 完成后无残留；取消、启动失败、PID 复用和 setsid 后代均覆盖。不需要模型即可先验证生命周期。

既有 `tests/benchmark/linux_supervisor_probe.py` 甚至明确断言成功退出后 detached 后代已被清理。因此，这里不只是漏了一条测试，而是原测试采用了不适用于“服务就是交付物”的生命周期合同。应保留临时进程清理测试，并新增任务服务移交场景。

### 2. 命令期限没有覆盖最后的管道回收：P0

`forge/tools/shell.py` 在 timeout 内等待进程和输出，但超时处理后又无期限等待进程/输出任务。Linux 清理只杀原进程组；调用 setsid 的后代可逃离该组并继续持有管道。

短小离线对照，配置均为 0.3 秒：普通子进程约 **0.304 秒**返回；持有管道的 detached 子进程睡眠 2 秒后才返回，实际 **2.066 秒**。这证明期限边界可被突破。Mailman 的具体后代进程树没有完整留存，因此其 30→1,391 秒的触发路径仍需专项追踪，但不能再将这一现象解释为模型推理太慢。

当前 `test_timeout_closes_inherited_pipes_after_parent_exit` 覆盖继承管道，但子进程没有设置 `start_new_session=True`；新反例补充了脱离原进程组的边界。此前全量 707 项通过不代表该路径已经得到验证。

**设计：** 一个绝对 deadline 贯穿启动、stdin、运行、stdout/stderr 排空和 cleanup；清理另设短且有上限的 grace。到期后停止 reader、关闭 transport，保存已有输出并返回确定的 timed_out/cleanup_incomplete。Linux 采用命令级所属进程范围，而不是依靠单个进程组推断全部后代；与上一项任务服务的生命周期分离。

### 3. 搜索预算只限制结果数量，没有限制搜索工作量：P0

`forge/tools/search.py:iter_files` 先将 os.walk 的全部文件累积为 list，之后 FindFilesTool 才匹配 pattern 和 max_results。因此 `max_results=100` 对全盘扫描时间没有约束。搜索在 `asyncio.to_thread` 执行，取消等待也不能自动停止正在遍历的线程。

另用 100 个子目录的临时合成目录做了离线验证：每个子目录都有一个匹配文件，`max_results=1` 最终只返回 1 项，但仍遍历全部 101 个目录。该测试验证结果上限并非工作量上限；没有再次在宿主或容器上执行全盘搜索。

**设计：** 流式遍历；同时设置 deadline、扫描项上限、输出字节上限、深度/文件大小限制和合作取消信号；默认从任务根目录搜索。需要系统依赖定位时先查询解释器/包管理器和明确安装目录。显式全盘搜索应返回扫描边界与截断状态，并跳过 proc/sys/dev 等虚拟文件系统，不能把预算中断显示为“确实无匹配”。Grep 同样需要文件大小和二进制/特殊文件边界。

**验收：** 无匹配、首项即匹配、大目录、虚拟文件、取消和慢文件系统；关注扫描项数、返回期限和线程退出，不能只断言返回列表长度。

## 验收层：需要更短、更可修复的反馈闭环

本轮 71 次 verify 请求，记录 69 份证据，其中 25 份 evidence_valid=false；19 份没有得到末行 JSON。这 19 份既包含检查语法/输出问题，也包含断言或被测程序提前失败，不能一律称作 JSON 解析缺陷。

`review_delivery` 调用 7 次，覆盖 6/20 题。首次 review 之后一共又调用 8 次 verify，**没有调用任何文件编辑工具**。已有反馈使部分绑定和断言补齐，但没有证据显示它引导出交付代码修复。delta_eq 本轮使用次数为 0，不能把新能力存在当成它已经贡献了成绩。

### 4. 将“提交检查”变为有限的修复机会：P1

现在 `_finish_declaration` 发现验收缺口后直接结束为 partial。模型可能直到最后一步才得到缺口，并已失去继续修复的机会。强制增加无限反思会浪费更多预算。

建议引入明确的 `prepare_delivery` 阶段：在预留预算内自动运行一次只读检查，返回少量排序后的、可执行的缺口。若属于可修复的调用错误、缺少验证或真实失败，允许最多 1–2 轮有预算约束的修复；相同失败指纹、没有新证据或预算不足时停止。未达到阈值仍必须诚实提交 partial/failed。

阶段迁移以具体反馈为依据：被测行为失败应修改产物；检查程序语法错误应修检查；输入身份未知应寻找来源；未知执行语义应改用结构化执行。不要把所有情况都变成再写一段 verifier。

### 5. 简化检查合同的使用，保留反弱化约束：P1

- 提供结构化 `argv + stdin + cwd` 执行规范，保留完整脚本或脚本 artifact ID，减少 heredoc、末行输出和 shell 链分类摩擦；不要根据复杂 shell 字符串推断它证明了正确性。
- 将检查状态分成编译/准备失败、执行失败、断言失败、通过、过期；保留原始证据，不把检查自身无法运行等同于已证伪任务需求。
- 检查复跑按稳定 ID 复用原定义；明确的检查修订应继承既有断言并记录原因。既不能让语法错误永久毒化验收，也不能通过改小目标、改输入或扩大容差抹掉真实反例。
- 要求 ID 由系统生成并提供明确映射，避免模型先使用任意别名、最终又登记另一组 req ID。保留原文依据，不能为提高内部通过率删除需求。
- 数值比较显式提供绝对/相对容差，容差必须有任务依据并在看到结果前确定；改成与输出完全一样的 expected 不是修复。
- 证据时效逐步依赖被测文件摘要、依赖身份、输入摘要、进程会话身份；对未知 shell 副作用仍保守失效，避免直接把全局 environment_epoch 判定删除。
- 交付类型区分代码、文件产物、环境配置、后台服务和信息检索。`run_forge.py` 对所有 benchmark 强制 `require_changes=True`，会错误要求 qemu 启动任务提交文件 Diff。

`recorded_assertion_passed` 只能表示已记录断言通过，不能自动等价于官方任务正确。输出文本也应与内部最终状态一致，避免系统标为 partial 而自然语言仍说全部完成。

### 6. 从“自洽”转向可证伪的行为证据：P1

本轮最清楚的反例是 WAL、ELF、终端和 Raman：自己生成的期望值、同一基址假设、输入回显、自己的拟合输出，都能产生漂亮的通过记录，却没有验证真正需求。

建议以通用方法改进，而不将本次隐藏答案写进提示词：

1. 操作数据库、二进制、配置等可能产生副作用的输入前建立可恢复副本和内容摘要，在副本上探索；文件“只读查询”不保证整个系统没有副作用。
2. 检查程序从独立来源或任务合同构造期望。记录参考来源、输入来源及重要假设；两种语言写同一个算法不自动构成独立参考。
3. 交互/服务任务以外部可观察副作用为准：文件真正生成、独立客户端完成协议、进程退出后会话仍可用；终端回显不能证明命令执行。
4. 公开样例之外加入由规则生成的输入、边界、反例和有依据的变换关系。隐藏答案不可进入模型上下文或通用回归测试。
5. 信息检索区分历史快照与当前数据过滤；无法找到历史依据时表达不确定，不声称已经验证历史答案。
6. 科学计算先确认列、单位、坐标转换和模型定义，再检查残差、参数稳定性和独立参考。这里尚未完成 Raman 坐标转换的独立重建，不能把峰位错误简化为某一个已证实的转换 bug。

## 预算与上下文：把计算花在新证据上

path-tracing-reverse 单题消耗约 30.9% 的本轮输入 token（含缓存）、19.3% 的模型请求，最终仍是近似产物。复杂题需要探索，但重复观测没有形成足够快的假设排除。

建议每次重试维护简短记录：当前假设、证伪方法、观测结果、下一次将改变什么。网络/依赖重试有独立上限；相同诊断不应不断换 URL。编译与安装步骤采用可轮询会话，保留最后有效产物，为验证和提交预留时间。

上下文保留当前目标、有效假设、已排除原因、关键文件位置与最新证据，历史大输出用可检索 artifact 引用。压缩后必须保留反例、任务约束和失败原因，不能只保留模型的成功总结。先测各类文本占比和重复传输，再决定是否重构 compactor。

已额外读取实际 wire 请求验证上下文规模：各题最后一条请求中，system 序列化约 1.69–2.71 万字符，工具定义约 2.23–2.38 万字符，消息约 4.07–23.59 万字符；14/20 题最后的消息内重复出现至少两份 Acceptance Discipline 标记。这是字符观测，不是 token 或账单估计。可以优先消融重复的任务/验收长文本，将稳定规则与动态状态分开、让 task_update 返回增量；工具定义是否按阶段缩减，则应测试其对可用能力与缓存稳定性的影响，不能仅为变短而隐藏必要工具。

既有日志修复不应推倒。本轮相邻记账事件间隙合计约 171.3 秒，20 题 Agent 累计时间约 14,592 秒；这不是主要的几十分钟卡顿来源。按日志长度估算，当前尾部算法校验读取约 0.575 GB，旧算法反事实约 43.56 GB；这是算法估算，非实际 I/O 计数器。

## 实施次序与对照实验

建议保留当前内核，以三个边界组织改造：执行层负责期限与进程所有权；证据层保存原始检查及修订关系；交付层决定是否允许有限修复及何时移交产物/服务。调度器管理整个 trial 生命周期，官方 verifier 结果独立记账。这样可以逐项验证和回滚，避免把来源登记、shell 字符串分类、服务清理和最终评分继续耦合在一起。

| 阶段 | 范围 | 先做的验证 | 再做的评测 |
|---|---|---|---|
| A：执行边界 | 服务生命周期、全程 deadline、有界搜索 | 离线生命周期与取消反例、流式搜索扫描预算；确保已有命令清理不回退 | 固定同一快照重跑 gRPC、Mailman、MCMC；qemu 另处理 verifier 环境 |
| B：验收闭环 | 有限 prepare_delivery、检查 ID/修订、交付类型、结构化检查 | 正确产物被坏检查阻塞、真实失败不能弱化、无修改服务任务可验收、超时后保留官方 reward | 同 20 题、同模型/推理配置/并发/预算做配对对照 |
| C：证据质量与效率 | 输入副本、独立参考、反例驱动、预算和上下文 | 使用合成案例，不固化当前隐藏答案；确认压缩保留失败证据 | 再从未分析题目中预先固定新的保留集 |

建议同题比较至少做多次重复，并记录每题由失败变通过、由通过变失败、模型调用、工具有效运行时间、超时、环境故障和输入量。先固定并发 5，不同时改变代码、并发、模型和推理设置。修复后的内部 completed 比例可以作为校准指标，但主要指标必须是官方原始 reward 和单位解题成本。

这 20 题已经被用于失败分析，今后属于开发/回归集。按此前排除 18 题及本轮 20 题的记录，89 题中还有 51 题未进入上述分析集；下载它们的镜像不需要读取隐藏测试或答案。不能继续在同一小题集反复调参后声称获得了总体泛化提升。

镜像缓存、Agent 依赖、verifier 依赖和任务要求安装的依赖必须分开。可以对评测外部依赖做预检和缓存，但若安装本身是题目目标，提前替 Agent 装好会改变任务难度。环境失败重验应使用原产物、单独 run ID，并保留旧失败；不修改原始 reward 文件。
