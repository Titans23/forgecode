# 修复前后两轮十题评测对比

## 结论

存在可测的运行时开销优化，但尚无整体解题能力或单题效率提升的证据。原始得分从 4/10 降到 3/10；没有新增通过题。此次只进行历史产物和轨迹分析，没有执行题目程序、请求模型或修改产品代码。

比较对象：旧轮 `2026-09-15__13-33-35`（并发 2）与新轮 `2026-09-15__16-30-01`（并发 6）。二者使用同一十题集合、同一数据集 SHA256、gpt-5.6-luna、Anthropic 兼容接口及 120 模型请求/240 工具请求/1800 秒配置预算；代码和并发同时变化。两轮实际 wire 均未携带显式 thinking/output_config/reasoning 设置，因此不能把推理配置传递能力的修复说成已提高了本轮推理强度。

### 排除提前服务失败造成的表面提速

只观察两轮均未以 server_error 终止的同一组七题（排除 CompCert、path-tracing、protein-assembly）：

- 通过数 **4/7 → 3/7**。
- 累计代理运行时间 **6405.16 → 6410.86 秒**，几乎不变。
- 模型请求 **315 → 354**，增加 **12.4%**。

这组诊断对照说明单题工作的总体效率尚未改善。七题子集不替换原始十题分母；也不是随机化实验，任务内容、模型采样和并发负载仍可影响结果。

## 哪些优化有证据

要求引用与验证分类的修复也在真实运行中生效：至少 **10 个仅空白不同的引用成功登记**；本轮命令对照旧冻结分类器，**4 条 Python heredoc 从 unknown 变成 behavior**，其中 2 条实际成功，失败的命令仍失败。这些收益减少了无效阻碍，但不是新增通过题。

日志追加算法从读取整份历史变为读取最后一条记录。原日志累计读取量按旧算法约 32.09 GB；新日志虽然从 104.01 MB 增至 122.04 MB，按冻结源码尾部算法推算的校验读取量约 0.437 GB。这是基于 JSONL 长度的算法估算，不是运行时 I/O 计数器。诊断数据将新轮旧算法反事实值另存，避免误称新轮仍全量重读。

此前同机器、相同锁和 fsync 的 500 次追加对照中，20.20 秒降至 9.51 秒，读取量下降 98.7%。这是最明确的工程优化。

实际轨迹中选定相邻记账事件的间隙合计 **470.76 → 168.90 秒**。POV-Ray 的此类间隙中位数 **265 → 47 ms**，MIPS **286 → 48 ms**。方向与日志修复一致，但这些间隙也含调度和运行时工作，不能全部记作磁盘节省。

预算父链和原生接口截断 usage 的修复已通过离线反例测试。本轮没有 explore_repository 调用，使用的也是 Anthropic 兼容接口；不能声称这两项修复在本次十题中直接贡献了得分或提速。

### 产物层：局部改善与回退来自哪里

- **POV-Ray：不是渲染能力退化。** 两轮版本与渲染检查均通过，SSIM 均为 0.8731。新轮唯一失败检查是源码身份，其中 `file_id.diz` 的 MD5 不符。旧轮从官方 2.2 目录下载源码归档，新轮改从 OS/2 ISO 提取 `POV22F.ZIP`。少通过的一题与源码包选择和字节身份有关；本轮不能据此断言运行时修复破坏了编译或渲染。
- **视频：公开样本更接近，但泛化没有改善。** 起跳/落地从 94/109 变成 50/68，起跳已进入公开样本容许区间，落地仍不在 62–64。隐藏视频起跳从 309 变成 104，仍不在 219–223，且离目标更远。两项官方行为测试仍均未通过。
- **电路：诚实报告改善，行为结果未改善。** 旧轮在 28 个官方行为输入中通过 2 个；新轮 28 个均输出 0。结构检查通过不能代替行为正确。新轮主动承认 gate network 未修好并提交 partial，减少了旧轮查表自证的虚假成功感，但算法能力没有得到提升。
- **MIPS：诊断更明确，没有首帧进展。** 新轮 30 秒官方测试仍不能生成 `/tmp/frame.bmp`，相关 3 项检查仍失败。代理反复定位 `I_Error`，最终明确 partial，比旧轮耗尽时间更早报告不足，但没有可验证的可运行交付。

## 仍然突出的机制问题

1. **自测与官方结果区分不足。** 新轮 POV-Ray、video-processing 的当前检查报告为 passed_checks，官方得分却为 0；overfull-hbox 的检查报告为 failed_checks，官方通过。新轮十题 acceptance_status 均为 unmet。不能把内部验收标签直接当作真实质量指标。
2. **检查数量不等于证据质量。** MIPS 的 verify 调用 7→16，仍未通过；电路模型请求接近翻倍，正式 verify 调用却 2→0。应检查任务是否把预算转化成有效的行为反馈，而非只统计工具活动。
3. **诊断工具尚未充分使用。** 新的只读提交前检查只有 POV-Ray、video-processing 各一次调用。两者随后只补 verify，没有修改交付代码。视频尝试继承旧检查同时重写断言，运行时正确拒绝；随后去掉继承验证，旧证据仍 stale。工具提供了机会，但没有实现稳定的“发现真实缺陷→修复→独立复验”过程。
4. **服务故障与任务失败须分别处理。** 10 个 server_error 请求集中在北京时间约 17:02:39–17:03:13。首个失败请求开始时本轮只剩 3 个代理活跃；CompCert 最后三次失败时只剩 1 个代理和 1 个请求。不能据此把错误归因于 6 个并发请求压垮服务。共享服务/上游瞬时异常、外部负载或累积限制均待核查。三个题仍算原始失败。
5. **来源锚定的剩余拒绝不是同一空白问题。** 新轮四次来源引用相关 task_plan 拒绝涉及省略号、增加引号或改写文字，不是纯空白差异。保留这些拒绝符合修复范围；不能把仍有拒绝等同于修复失效。

下一步应优先验证交付场景和独立测试的有效性，解决 POV-Ray 的回退，再做相同代码在并发 2/6 下的受控比较。此处是后续实验建议，本轮没有启动任何重跑。
