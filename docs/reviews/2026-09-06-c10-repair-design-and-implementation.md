# 并发十题评测后的修复设计与实现

## 目标

解决本轮日志已证实的收尾循环、检查器修订无法解除义务、控制器退出缺审计和缺失官方结果导致漏计用量。保持单一 TurnRunner、现有权限和预算；不把失败解释成通过，不写题名特判，不自动启动下一轮。

## 状态设计

### 要求身份与完成声明

新要求身份由 task_id、原文 source_quote 和可选稳定 clause_id 决定，condition 不再参与 ID。一个引用包含多个不同约束时使用不同 clause_id；重复同一来源/子条款时保留首次登记的完整条件和检查解释，后续较弱措辞不能替换原义务。计划的显式补充仍可添加新来源或子条款。

finish_task 的兼容性入口仅在没有任何要求时登记一次无计划合同。一旦存在合同，finish 只读取既有集合；附带的新措辞不会修改它，返回 metadata 始终给出实际要求。因此重复 finish 不再扩张 ID 集合。已有 session 中的旧 ID 保留，避免其历史证据失去关联；不自动合并旧 session 已积累的多个义务。

这种处理固定已登记解释，不代表自动证明全部要求已提取。明确的新要求应通过规划入口登记；同一来源新的子条款不能悄悄替代旧条款。

### 检查器修订与证据替代

每次 verify 实际执行生成 verification_id，并持久化 output_checks。修正检查器时可提交 supersedes=[旧 ID] 和 revision_reason，新的真实执行仍走相同授权、进程和工作区证据流程。

旧失败只有在新执行成功、cwd 相同、明确引用旧 ID、给出修订理由，且所有旧输出断言均被完整保留时才能解除。比较字段包括输出 key、操作符、expected（类型也保留）、requirement_id 和 expected_source；旧关联要求必须在新执行的 asserted_requirement_ids 中。缺失断言、降低阈值、改变期望来源、换目录、缺少原因或新执行失败，均不能解除旧失败。没有结构化输出断言的旧检查不自动获得替代资格。

这一实现允许修正脚本语法、执行程序和 JSON 输出方式，但不会自动批准改变检查合同。它验证的是可观察断言合同保留，不是任意程序的语义等价证明；模型仍可能编写低质量检查，这是已有自主验证的限制。历史事件保留旧运行、修订关系与新执行。当前/过期失败反馈显示验证 ID 和修订入口，限制重复粘贴长命令及错误文本的长度。

### 失败终止

failed 缺少 blocked_reasons 时从已要求的 summary 补齐失败原因，保留旧字段兼容；blocked 仍需要具体原因并受运行时外部阻塞证据检查。电路任务这种已诚实报告算法错误的场景，不会再因失败出口字段遗漏消耗纠错预算并变成 tool_protocol_exhausted。

### 控制器与日志生存期

数据集入口使用独立于 Harbor result.json 的 controller-state.json：记录控制器 PID、子进程 PID、启动时间、每 5 秒 heartbeat、退出码/时间和异常类型。状态通过临时文件原子替换并 fsync，不保存完整 argv 或 env。输出目录复用不能覆盖既有控制器审计。

读取状态时，超过 60 秒没有更新的 running 标为 unresponsive，不宣称 agent 仍在工作，也不根据心跳缺失擅自杀进程或付费重放。正常子进程退出只标 exited，不等于题目完成；官方 job/result 继续独立表示验证收尾状态。硬杀控制器时仍可能没有退出记录，但旧心跳不会无限显示正常运行。

agent 会话直接写入 /logs/agent/forgecode-state，退出时保留原平铺导出以兼容旧分析工具。外层 Harbor 超时中断退出代码时，已经写出的 session 不再依赖最后的 cp 才能保留。启动元数据区分 kernel_max_seconds 与数据集外层 timeout multiplier，不提高原生任务超时。

这修复的是可观测性和日志保留，不能宣称已证明或消除了历史控制器消失的具体原因；也没有实现自动接管孤儿容器或恢复官方验证。

### 汇总口径

先区分官方结果是否存在，再从所有任务目录收集内核用量，包括缺 result.json 的任务。缺官方结果时仍保留内核 timeout/model 故障，不把 exit_code=0 解释成通过。终止 payload 不存在时，从持久 session 的请求生命周期恢复可观察用量；通过事件 UUID 去重平铺导出与嵌套日志的副本，忽略正在写入的残缺尾行。

没有终止 payload 或可用 session 的任务列入 telemetry_missing。此类用量未知，不能当零成本；原始 reward 和有效计分口径不修改。

## 验证与风险

新增旧代码失败场景已复现：同源改写增加要求、failed 出口拒绝已有 summary、缺少检查器修订路径、缺 result 时遗漏模型用量。补充测试覆盖连续 25 次完成重试保持合同、独立子条款、旧 ID 恢复、真实 Python 检查器修订、弱断言不能清除失败、真实控制器子进程退出码、过期心跳与会话副本去重。

最终复验：Windows 全量 613 passed（223.80 秒），离线 Linux 全量 613 passed（75.16 秒），两端均仅有一条既有飞书 SDK 依赖弃用警告。compileall 与 git diff --check 通过。全量测试期间发现普通 inspection 可没有 active task 的兼容性遗漏，已修复空状态访问，并用原有四项回归和两端全量验证确认。日志分别保存在仓库根目录 .test-c10-windows-final.log、.test-c10-linux-final.log。

此次不开展 benchmark；算法策略、自然语言合同完整性和程序语义等价不由上述修复自动解决。

## 历史用量口径更正

上一份分析报告的 27,229,371 是九题 payload 的 input_tokens 原字段合计，未含 cache_read_input_tokens；而旧 summarize 的 input_tokens 字段包含缓存读写 token。两列不能直接相减比较。按汇总器原有一致口径，当前九题输入合计为 29,676,731，输出 336,536，模型 609、工具 757；overfull 遥测仍缺失。原字段 27,229,371 与缓存读取 2,447,360 分开保留，不据此推断实际账单。原报告的跨轮输入增幅和输入漏计量应以这一更正为准。
