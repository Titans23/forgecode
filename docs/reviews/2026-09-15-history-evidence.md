# 历史评测证据复核：能力失败与服务失败必须分开

复核日期：2026-09-15。只读分析现有官方结果、验证器输出、会话事件与冻结代码快照；没有调用模型、启动评测、执行题目解法或修改运行时代码。

## 1. 核心结论

1. 最新重启轮原始得分是 **0/10**，但它不是一次可评价解题能力的完整运行：十题全部被模型服务或响应协议问题提前终止，六题随后又发生验证环境故障。不能据此认定最近合同修复降低了通过率。
2. 最新轮没有任何 `verify`、`finish_task` 或 `inherit_checks_from` 调用。真实运行尚未检验新合同继承和重复收尾保护的收益；测试用例通过与真实评测通过是不同证据。
3. 最有诊断价值的是 9 月 14 日 11:39 轮：原始 2/10，正常结束且通过 1/10；既存在真实算法/交付失败，也存在 52 次完成申请、46 次拒绝的流程损耗。取消完成门禁不会让现有错误产物自动通过官方测试。
4. 9 月 7 日并发十轮全在环境初始化失败，零模型调用；9 月 6 日轮官方结果缺两题。不能把它们与后续完整运行当作只改变单一变量的对照实验。
5. 架构设计的首要方向应包括运行有效性分层、外部服务故障恢复与暂停、可复现环境、薄化验收协议、可靠交付和独立行为验证；并非根据几个 raw 分数直接推导需要多代理或全面重写。

## 4. 最新重启轮为什么仅约 25 分钟

C 控制器 16:42:42 启动、17:08:02 退出，共约 25 分 20 秒。十题代理阶段合计约 1,195 秒（并发阶段求和），每题只有约 45–417 秒，远早于预算终点。剩余墙钟还包含队列、容器准备和官方验证。

95 次模型请求的事件分类：

- 正常完成 22 次。
- `server_error` 后重试 61 次，最终因 `server_error` 失败 9 次。
- `timeout` 后重试 1 次。
- `stream_termination_missing` 1 次，电路题之后曾恢复继续执行。
- `incomplete_tool_call` 1 次，MIPS 最终结束。

因此只有约 23% 请求正常完成，计数包括重试，不能据此计算模型推理效率。HTML、CompCert、overfull、path、protein 五题工具调用为零；POV-Ray 和视频各只执行一次 `task_plan`。这解释了大面积未交付和运行短，而非完成保护把十题过早判败。

`server_error` 是记录中的归一化类别；这些日志没有给出足以区分上游模型、转发服务或网络链路的 HTTP 原始细节，不能进一步断言具体责任方。验证器原始日志则直接显示 TLS 连接中断、下载超时或命令缺失，支持网络/依赖问题存在。

### 截止时间

C 十题 `agent_result.metadata.outer_deadline_bound=true`；有效内核预算 HTML 1170 秒、overfull 720 秒，MIPS/path/protein 1770 秒，其余 1800 秒。这与外层原生时限减余量再取配置上限一致，证明适配器传入了预算。

## 6. 旧失败对设计的约束

A 是可用的能力诊断样本：电路数值计算错误、MIPS 未生成帧、CompCert 没有编译器产物、path 隔离执行失败、视频定位错误。蛋白“条件矛盾”只由模型自述，官方证据仅是未交付，不能断言题目无解。

S6 的主要可复用现象包括：MIPS 用完 120 次模型预算；电路因 `finish_task` 参数不满足失败理由约束耗尽协议恢复；POV-Ray/蛋白内核时间耗尽但缺官方结果；overfull 官方通过却外层 750 秒超时。这些分别支持策略预算、局部纠错、控制器持久化和统一截止时间的需求，不能混为同一种架构缺陷。

S7 官方 exception 显示 Docker Compose 初始化期间失去 Docker Desktop Linux Engine API 管道，十题均未进入模型。它的 0/10 说明评测环境失效，不能支持任何模型优劣或完成判定结论。

## 7. 由证据导出的优化优先级

1. **运行有效性必须成为第一类状态。** 分开 agent 服务可用性、工具执行、候选产物、内部验证、外部评分；主分类和叠加故障都保留。报告始终保留计划题目分母和未评分原因。
2. **服务故障需要可恢复边界和批次熔断。** 目前单题会短退避重试，但系统性 server_error 持续时队列仍把所有题逐个消耗完。设计批次健康状态、暂停新题、保存检查点、用户恢复入口；不能把局部“安全重试”扩大为重放未知副作用。
3. **验证环境要可复现准备。** 预热或版本固定的依赖准备和网络预检应独立于解题，不让 agent 看到隐藏测试。区分 uv 缺失、curl 缺失、下载失败、真实断言失败。恢复环境后对旧候选重验必须标注为事后重验，不覆盖原始轮次。
4. **减少验收协议占据模型注意力。** 稳定合同引用、明确字段差异和候选提交入口值得保留；同时必须允许未充分验证的候选结束并交由官方评分。弱自测不是正确性证明，更多 JSON 字段不是更强验证。
5. **提升可观察的解题策略。** 构建任务早做最小编译与依赖检查；算法任务早做独立参考/边界测试；隔离交付早做干净环境执行。不能把隐藏测试阈值写进泛化策略。
6. **未来实验分层。** 在用户重新授权前不跑新评测。先离线回放真实服务中断、未闭合工具、合同改写、反复完成、期限临界事件；再对固定代码/模型/预算/并发做服务健康条件下的对照，并加入未参与修复的保留任务。报告 raw reward、有效运行覆盖、产物交付、完成协议开销和费用口径，避免只追逐单个十题分数。

上述结论支持保留有效的执行器与持久日志、重构存在摩擦的状态/验收边界，并改善服务和评测控制；不能从当前历史记录量化这些因素各自造成的通过率损失，也不能预告优化后的成绩。
