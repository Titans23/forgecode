# Luna 并发二评测：失败归因与架构调整决策

## 范围与结论

分析对象：`benchmark/runs/harbor/terminal-bench-2-1f4e481-luna-c2-20260914-113857/2026-09-14__11-39-31`，代码版本 `1f4e48103a32fa791371276dff97f9b9d8653a3b`，模型 gpt-5.6-luna，固定十题，并发二。依据为官方 result/CTRF、持久化 session 事件、当前运行时代码。没有新增模型调用或重跑评测。

决策：保留单一 TurnRunner、ToolExecutor、权限与执行记录、持久会话和评测控制器；有边界地重构验收证据/完成判定子系统，同时修正截止时间和工具纠错策略。当前证据不支持全面重写，也不支持认定增加多代理或更换模型就能解决问题。

## 成绩口径

- 十题均有官方结果，控制器正常退出，约 11:39—14:09，共两小时三十分钟。
- 原始 reward 为 2/10：distribution-search、break-filter-js-from-html。
- HTML 虽 reward=1，但 agent 在 1200 秒被外层强制终止。因此正常完成且通过为 1/10。
- overfull-hbox 在 750 秒超时，验证器另发生 uv bootstrap 故障；其产物正确性不能据零分定论。
- 主分类是正常通过一题、产物/代理失败六题、代理超时两题、验证环境失败一题。超时信号实际涉及三题，overfull 的主分类掩盖了其超时，不能重复累加类别。
- 记录模型调用 561 次、工具调用 738 次。汇总输入 26,471,265 tokens 含缓存口径，输出 313,150；不是实际账单，也不能把所有用量归因于门禁。

## 为什么形式上更严格，正确率仍然低

### 1. 验收合同仍可能遗漏真正的语义

视频题把“检测跳跃”映射为来自视频、区间非空、格式正确；这些都不能证明起跳/落地定位准确。POV-Ray 的来源身份、编译成功和渲染成功，也不能代替规定目录中文件完整性。引用用户原文、输出 JSON、关联 req ID 可以提高可追踪性，却不能自动提高检查器的独立性和区分能力。

因此系统会出现两种问题：弱自测通过却交付错误；自测合同修订又被形式约束反复拦截。仅增加提示或放宽完成门禁都不能同时解决两者。

### 2. 检查器身份与自然语言说明耦合

`forge/runtime/completion.py:436` 的 checker_revision_covers 对 key、operator、expected、requirement_id、expected_source 做完整合同集合比较。最后一个字段是模型填写的自然语言说明。

POV-Ray 最初记录 `e33ac694c72241a4897794bf82a7f828` 和最终记录 `08d5f37ec5aa4cd5aaa7775d4dbc0251` 存在明确 supersedes 关联，但五项共有断言的 expected_source 全部改写，其他上述字段保持相同。这已经足以阻止该旧记录被替代。视频题旧记录 `e8ba03d98766498da86fbf1bf73725bf` 与最终 `5451a897fb294537bb365edb56ee43ae` 同样存在明确关联，三项共有断言来源说明改写，takeoff/land 还改变了 requirement_id，不能当成纯措辞问题直接放行。

这不是简单的“supersedes 没传入”：当前实现按设计拒绝了这些合同变化。问题在于设计把解释文本当作稳定身份，又没有告诉模型究竟哪个字段不一致。此前单测证明的是严格保留合同的理想路径，未覆盖真实模型反复改写来源说明的路径。

### 3. 结束任务变成新的解题负担

全轮 finish_task 共 52 次，其中 46 次 completion_rejected；HTML、POV-Ray、视频三题合计 44 次 finish，其中 42 次拒绝。这是调用数量，并非“42 次本来可以通过”，也不是精确的时间或 token 损失。

`runner.py:563` 的失败反馈在同类错误第三次出现时提供通用提示，缺少按验收义务差异生成的修复操作。`runner.py:556` 对工具协议错误却使用累计预算，并以 min(2, 配置) 限制恢复次数。结果是复杂收尾可反复尝试，某些局部参数错误却较快导致整题退出。应调整这种不对称，但不能取消全局预算。

### 4. 截止时间没有统一进入内核

内核本轮预算为 1800 秒，外层部分题目只有 1200/750 秒。agent 适配器 `_run_command` 依据内核时间构造命令和额外清理宽限，不能据此保证 Harbor 外层会等待。必须把实际有效截止时间传递到模型预算提示、工具超时和收尾逻辑。

### 5. 证据失效范围偏粗

`executor.py:263` 附近对 verify 以外的 process 工具调用统一增加 environment_epoch，`completion.py` 要求证据与当前 workspace_revision/environment_epoch 匹配。此设计保守但可能把仅查询进程环境的操作也视为全局失效。POV-Ray 最后 epoch=60 可见频繁进程调用；这不能单独证明六十次都属于错误失效，需要记录级差分测试。

### 6. 单轮成绩不能隔离模型因素

这是十题单次样本，没有相同代码、模型参数、预算和环境下的重复配对实验。并发改变也改变墙钟表现与资源竞争。不能据此量化 Luna 能力上限、宣称 c2 比 c10 更差，或把单次分数差归因于模型。多个任务的算法/构建失败说明解题策略需要改进，但其与框架摩擦的贡献尚未分离。

## 建议的架构边界

### 保留执行基础

保留 TurnRunner、ToolExecutor、TurnState、事件日志和控制器。此次结果完整收尾，对可观测性修复提供了正向证据。没有证据显示重新设计工具总线、UI、存储或多代理调度能直接修复上述失败。

### 重构验收证据子系统

建立三类独立记录：

1. Requirement：原文来源标识、条款标识、约束及来源等级。外部要求与模型推导假设分开，不能让模型自选断言自动变成用户硬要求。
2. CheckSpec：稳定 check_id、版本、关联 requirement_id、结构化期望、固定 source_ref、解释文本。解释文本不参与身份比较；数值阈值、来源标识、要求绑定仍参与合同校验。
3. CheckRun：执行事实、产物版本/依赖指纹、成功失败/执行错误、输出及 supersedes 关系。历史不可变；当前有效性通过解析关系得到。

探索性命令失败、检查脚本执行失败、真实验收断言失败分开处理。真实失败必须由对应义务的当前成功证据解除；探索性失败不永久升级为验收义务。跨要求绑定、修改来源或降低阈值不能仅凭模型解释清除旧失败。

返回结构化拒绝原因，例如 assertion_contract_changed、requirement_binding_changed、evidence_stale、checker_execution_error，并精确列出缺失断言/字段差异。提供引用旧 CheckSpec、仅修订执行脚本的操作，减少模型重抄合同。旧历史迁移要保留来源歧义，不能批量默认为等价。

### 分开交付状态与正确性判断

区分执行终止、产物已提交、内核验证状态、官方评分。证据不足可以保存并提交候选产物，同时明确未验证或失败；不应只有“证明完成”与“持续尝试”两个出口。benchmark 的 reward 始终由官方 verifier 决定，不能靠修改内部 completed 状态提高成绩。

### 预算与策略调整

- 有效 deadline 取用户/内核预算与外层预算中最早者，并减去必要清理时间；逐层传递，工具超时不得超出剩余时间。
- 工具协议恢复按连续相同错误及近期窗口计数，保留总上限。合法调用后允许局部恢复；相同输入错误不无限重试。
- 对相同证据状态的重复 finish 返回同一诊断及具体修复入口，触发复盘/候选提交，不靠改措辞循环。
- 用依赖范围改进证据失效；未知 shell 副作用继续保守失效，不能简单信任模型声明“只读”。
- 构建任务尽早验证依赖和最小产物，算法任务尽早建立独立参考/边界用例，隔离运行任务尽早检查产物自包含。允许明确报告无法验证的部分，不伪造参考答案。

## 实施与验证顺序

1. 先将本轮真实事件整理成脱敏离线回放用例：来源说明改写、要求绑定变更、检查器语法错误、跨版本证据、13–17 次 finish、累计局部参数错误。验证旧实现能重现拒绝模式。
2. 完成 CheckSpec/CheckRun 与结构化拒绝反馈，保持旧 session 可读；用“相同合同修复可通过、减弱/换要求不能通过”的成对用例验证。
3. 接入有效 deadline、局部协议恢复及有限收尾；测试保证不越过外层时间、不隐藏失败、不丢日志。
4. 对验证环境做可复现预检，避免把 uv 引导失败计作普通答案失败。依赖准备不能让 agent 访问隐藏测试内容。
5. 用户授权后进行对照评测：同模型同预算同任务同并发，分开比较基础修复与证据重构，避免一次改动所有变量；重复运行并增加未参与调试的保留任务。

对照同时报告固定十题 raw reward、无超时通过数、环境失败、完成拒绝次数、重复无效操作、验证耗时与用量。预期首先减少无效收尾与非正常超时；正确率提升必须由新运行证实，不承诺某个百分比。
