# 2026-09-04：连续性修复与冻结对照

## 证据先于修改

新增 `tests/runtime/test_continuity_contract.py` 的前四项探针在修改前全部失败：

1. 后一轮复用 provider tool-call ID，前一轮的成功记录掩盖了后一轮未完成的副作用。
2. 约 12 KB 的失败输出在模型总结前被缩短，中间的唯一根因丢失。
3. 同类中等输出被缩短后，没有可供受控读取的 artifact ID。
4. 压缩后保留的最近工具结果使输入仍超过约 60% 的目标预算。

修复采用轮次标识、稳定结束事件标识、原始用户指令锚点、先总结后缩短、完整输出 artifact 和成对移除历史单元。继续任务不会用“继续”替换原目标；后续用户指令随任务状态保存。旧 JSONL 不批量改写。

## 其余内核修复

- Windows 使用受控启动器：进入 Job Object 后才启动实际命令。关闭 Job 清理后代进程，不依赖仍然存活的父 PID；POSIX 保留进程组清理。实现参考微软 Job Objects 与 AssignProcessToJobObject 文档。
- stdout/stderr 超过内存上限时完整写入内容寻址 artifact，模型得到头尾和读取 ID；在子目录执行时仍归档到统一工作区上下文目录。
- checkpoint 执行后记录失败不再谎称操作被拒绝、未执行；标记结果不确定，要求核查。
- 删除 task_update 的总结关键词门禁。计划关注路径不再被提示词升级成用户授权范围。
- 隐式空白检查改为显式 `TaskPolicy.require_diff_check`；原测试保留并明确请求该契约。
- 可选验收映射记录用户原文、可观察条件、独立检查方法。原文引用必须来自真实目标或后续用户指令。映射是模型解释，不是权限或独立验证。
- 调用方可显式要求输入文件哈希和逐项覆盖。测试证明：修改参考输入后，即使自测退出 0，也不能满足输入完整性契约。benchmark 不按题名注入哈希或解题答案。
- benchmark 明确传入新任务/继续任务关系，省去对已知任务进行模型路由的请求。

## 验证与环境

2026-09-04 恢复后最终完整回归：Windows Python 3.12.14 为 562 passed（192.35 秒）；Linux Python 3.12.11 为 562 passed（74.88 秒，不含安装时间）。两端均仅有已有的飞书 protobuf datetime 弃用警告，无跳过项目。另通过基线适配器 CLI 探针、Bash 安装脚本语法检查、compileall 与 git diff --check。

Linux 从镜像 Python 3.13 改为旧评测实际使用的 3.12.11。第一次运行发现测试子命令的 PATH 仍指向镜像解释器，已修复。MCP HTTP 测试的原始 5 秒就绪等待在该环境失败，stderr 无错误且服务进程未退出；改为使用产品现有的 10 秒连接契约后真实连接和工具调用通过，没有跳过 MCP。

运行依赖从仓库 uv.lock 导出为 `benchmark/harbor/runtime-requirements.txt`，含精确版本与哈希；安装先校验依赖哈希，再以 --no-deps 安装当前包。Python 3.12.11 缓存在 D 盘已有 Harbor cache 的 python 子目录。测试仍在一次性容器中执行，不挂载 .env 或用户会话。

Windows 完整测试从此前约 116 秒变为约 173 秒，包含新增测试和每个命令的受控启动器开销；这不是模型评测成本数据，不能据此宣称整体成本降低。

## 对照方式与验收边界

旧版独立工作区：`benchmark/runs/baselines/eff5909`，detached HEAD，内核源码不修改。

`--source-dir` 冻结被测源码；被测源码与驱动不同目录时另冻结驱动。仅用于历史评测的 `LegacyBaselineHarborAgent` 适配旧 CLI 缺少内部时间预算参数的接口，并向安装目录复制同一依赖锁。旧版用外层 1800 秒 watchdog，新版由内核执行 1800 秒预算，外层仅留取消清理宽限。这不是产品中的双内核开关。

固定十题、模型、120/240 调用预算、1800 秒、并发 6、Harbor 重试 3、setup multiplier 12、安装重试 8/间隔参数 30 均保持。旧版与新版不同时各开六并发。不使用 --force-build，不修改隐藏测试或按题名编写方案。

评测总结保留原始 reward；区分内核时间耗尽和 verifier 超时。旧未完整结束的轮次不能充当最终验收轮次。

以上证明执行与恢复缺陷得到修复，不证明任务算法已正确，也不保证通过五题。下一步必须用完整官方评测检验；每轮先逐题复盘，再确定有证据的修改。达到五题后冻结候选源码，再跑完整确认轮；连续两轮均至少五题才完成目标。
