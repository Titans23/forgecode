# ForgeCode 下一阶段优化路线

日期：2026-09-17。当前为规划，未实施代码修改或启动评测。

## 决策与目标

基线固定为最终 89 题：原未 server_error 的 51 题 + 38 题重评，41 通过、46 未通过、2 未判分，最终通过率 46.1%。后续修复以这份逐题记录查回归；它不是严格受控的单次运行基线，因果比较需重新固定运行条件。

下一阶段优先减少框架自身制造的失败，再改善交付和验证，最后优化复杂任务的求解过程。保留现有 TurnRunner、统一工具执行器、共享预算、持久会话；围绕已有接口做可独立回退的修改。当前不安排全架构重写，也不把多 agent、增加模型调用数或延长所有任务预算作为默认解法。

用三个目标判断改动是否有效：

1. 模型发出的合理操作能被准确执行，框架不给出不可操作的恢复提示。
2. 实际交付与完成判定一致，检查器错误不会被误当成产物错误，服务不会只在自测期间存在。
3. 在固定预算下提高独立全量通过数，并明确报告回退、调用成本和基础设施故障。

## 阶段 0：固定基线与故障复现集

已有材料包括最终 89 题数据、48 题分类、框架缺陷审计和离线复现脚本。先将这四者关联到题名、trial 路径、源码摘要、模型/provider、有效期限、结果来源，保留原始文件不改分。

把已确认的复现转为回归测试，期望描述正确行为；不要把“当前会误拒绝”写成长期正确性断言。诊断脚本用于证明旧问题，回归测试用于保护修复。

本阶段主要是整理，不要求重跑模型。产物：可复核的基线清单与四组独立复现用例。

## 阶段 1：修复明确的框架缺陷

### 1A. Agent 启动隔离（最高优先级）

涉及 benchmark/harbor/forgecode_agent.py、安装与 supervisor 启动链。

- 从安装包的稳定入口启动，避免任务 cwd 中 benchmark.py、benchmark/、forge.py 等同名文件影响导入。
- 同时覆盖 supervisor 和 run_forge；保留任务的真实工作目录。
- 在实际安装环境中验证，不能仅以开发环境 PYTHONPATH 对照通过作为修复完成。

验收：相同碰撞 fixture 在修复前失败、修复后能启动；正常任务入口不退化；缺少真实依赖时仍返回准确诊断。使用一次性 Linux 容器，调用本地假模型或不调用模型，禁止携带真实凭据。

### 1B. 权限分析修复

涉及 forge/permissions/risk.py。

- 区分命令执行位置、命令存在性查询、字符串、注释和脚本输入，修复 command -v sudo 误判。
- 保留换行与 shell 语句边界，避免把下一行变量赋值纳入 rm 删除目标。
- 建立统一命令分析结果供权限层使用，减少各处独立正则产生相互矛盾的判断。
- 先支持可以可靠解析的范围；复杂嵌套或未知语法保留明确的保守结果。根据实际 shell 区分 POSIX 与 Windows，不把同一套分词规则套用到两者。
- 不关闭权限检查，不通过简单关键字白名单或按换行切割修补复杂语法。

验收：合法查询、多行明确路径操作不再误拒绝；实际提权、宽泛删除、命令替换中的危险操作仍按既定边界处理。纯分类测试不执行危险命令，运行测试仅使用临时目录。

### 1C. 验收修复路径一致性

涉及 forge/runtime/check_contracts.py、completion.py、forge/tools/verify.py。

- 明确区分检查器执行异常、产物断言失败、环境不可用和证据过期。非零退出码不足以自动证明是哪一类，保留 unknown。
- 对有结构化断言的检查继续保持精确继承，不能降低阈值或移除需求。
- 对没有 output_checks 的检查，提供可执行的修复方案或准确限制说明；不要提示一个必然拒绝的继承调用。
- 记录旧检查、修复理由、保留的需求与新证据。修复检查器不等于原要求已满足，只有新的有效行为证据才能建立完成依据。
- 命令内部断言与 JSON 输出检查均保持可用，避免逼迫模型将所有检查重写成一种协议。

验收：检查器拼写错误可以走明确恢复流程；同命令重新成功能解决原失败；改成空命令、仅打印成功、降低断言等不能清除真实未满足要求。

阶段 1 不引入完整依赖图、新规划器或新多 agent 调度。先把明确 bug 修小、修透。

## 阶段 2：稳定评测条件与任务交付

### 2A. 验证环境与批次控制

四题验证器 uv bootstrap 失败、两题 verifier 超时，需要与产物故障隔离。

- 对官方验证流程所需依赖做预检，在规则允许的前提下使用固定版本缓存或预构建；不修改隐藏断言和阈值。
- 对两个超时任务保存验证日志与执行阶段，检查是依赖阶段卡住，还是提交产物在验证中挂起。没有保留可执行产物时不能声称可以只重跑 verifier。
- 固定网关发现/连接配置，启动前验证模型可用性；批次连续发生服务故障时暂停领取新题，保存队列，恢复后唯一续跑。
- 输出 error_origin 与失败阶段，不能只记录统一 server_error。日志脱敏，保留足够的上游错误类别和重试信息。

此处是在巩固评测基础设施，不重新把当前 48 个失败归因于已解决的旧 server_error。

### 2B. 最终交付检查

文件任务与服务任务分别增加可执行检查，以原任务需求为依据，不按 benchmark 题名硬编码。

- 文件：目标路径、文件类型、非空、允许修改范围、目录允许内容、必要副产物。
- 构建：可执行程序的最小行为；覆盖率任务实际运行后出现所需数据。
- 服务：从独立客户端检查实际 URL/协议与内容；agent 完成后仍存活。测试用临时服务和待交付服务分开记录。
- 自测临时文件进入指定临时目录；只清理已登记的测试产物，不能删除用户文件或按猜测清空输出目录。
- 在现有进程工具上补服务身份、就绪检查和受控终止信息，优先复用已修复的进程生命周期能力。

验收：能检出“自测成功但服务被脚本终止”“只有端口监听但返回 404”“目录残留编译文件”“编译成功但没有覆盖率数据”等负例，同时正常服务交付仍成功。

## 阶段 3：改进证据有效性和模型使用工具的成本

这部分存在设计风险，但失分收益尚未证明，必须分离实验，不与阶段 1 大批混改。

### 3A. 有针对性的证据失效

从当前全局 workspace_revision/environment_epoch 机制渐进改进：

- 记录检查依赖的文件与必要环境信息；受影响才失效。
- 明确只读的内建查询不制造环境变更；未知 shell 仍保守处理，不信任模型自行声明只读。
- verify 中的服务启停或依赖安装也需要被观察，避免永久豁免带来漏失效。
- 服务证据包含服务身份和实时就绪状态，不能只凭历史测试成功。

先覆盖窄范围的文件依赖与服务状态。未知依赖回退到当前保守策略，不一次构建任意程序的完整副作用分析器。

验收：无关只读检查不让全部验证过期；代码、依赖或服务真的变化时旧证据不能用于完成。

### 3B. 工具反馈简化

- 参数错误返回具体字段、允许类型和简短合法示例，减少反复试 schema。
- 检查执行结果明确区分“工具未运行”“运行失败”“验证未建立”“验证通过”。
- 验收冲突列出发生变化的断言/绑定，直接给出可行的修复入口。
- 前序失败后，只有确认依赖它的操作才讨论能否取消；当前缺少可靠依赖信息时维持安全串行语义，不为了减少错误计数执行全部后续操作。
- 保留详细日志，但给模型的恢复反馈以当前最关键的一个问题为主，避免重复灌入长串历史错误。

衡量的是实际减少的恢复请求和完成时间，不是让日志看起来“错误更少”。

## 阶段 4：复杂任务的求解与预算

19 题语义错误、10 题无有效产物、5 题指标未达标需要更好的工作策略。以下属于待验证假设，不承诺等价于模型能力提升。

- 先建立最小可信基线，再扩展实现：先小尺寸数值正确，再并行/优化；先程序能运行，再完整训练或渲染。
- 输入保护：复杂转换前记录原输入摘要；自测使用副本，避免破坏恢复任务的原始数据。
- 独立验证：使用任务提供的参考、数学性质、小型可信算例、负例和边界值。不能从当前实现反推预期值来“证明正确”。
- 指标分解：FastText 的准确率和模型体积分别检查；渲染检查具体误差来源；性能任务在稳定资源条件下测量，避免把一次抖动当优化效果。
- 阶段预算：环境准备、首个可运行产物、主要正确性验证、最终交付各有检查点。显示真实剩余期限；给最终验证预留预算，不额外扩大总预算。
- 无收益重复时调整策略。先根据结构化错误和进展观察触发提示，不用笼统的“连续 N 次失败立即停止”扼杀必要调试。

首轮不增加默认调用上限，不启用广泛并行子 agent。先证明现有单 agent 的执行与验证链路可靠。

## 实验路线与开始下一阶段的条件

### 第一级：离线机制测试

覆盖入口碰撞、权限解析成对样例、验收修复、不相关变更与证据有效性、服务保留/终止、临时文件管理。使用 Windows 本地测试和 Linux 一次性容器测试覆盖实际运行平台差异。

通过条件：已复现缺陷消失，对应安全/正确性负例仍能检出，既有相关测试没有回退。此级不调用真实模型。

### 第二级：固定 12 题集成回归

建议以下题集；它是已分析题目的回归集，不是未见泛化集：

| 目的 | 题目 |
|---|---|
| 启动/权限/验收恢复 | portfolio-optimization、compile-compcert、make-doom-for-mips、torch-pipeline-parallelism |
| 最终交付 | pypi-server、sqlite-with-gcov、polyglot-c-py |
| 语义失败保留为对照 | filter-js-from-html、torch-tensor-parallelism |
| 已通过的回归保护 | kv-store-grpc、mailman、build-cython-ext |

环境依赖先预检，未过预检不消耗解题预算。冻结模型、provider、reasoning 配置、有效预算与候选源码，工作并发暂固定为 4；这是控制变量的选择，不是声称并发 4 最优。

每一阶段单独形成候选。若要判断特定机制的收益，对照冻结旧版本与该阶段新版本；只看 12 题与历史结果的单次增减不足以证明因果。出现回退时，先用确定性重现或有限重复确认，避免立即扩大到全量。

### 第三级：独立完整 89 题

启动条件：机制回归通过、无未解决的确定性框架回退、验证环境可用，定向集成中的新退步已经解释。

完整报告至少保留：

- 原始完整运行分数和逐题增减；所有题均留在分母。
- 故障重评另表，不以历史最好值替换原始分数。
- 启动失败、工具误拒绝、检查器错误、服务/验证故障分开。
- 模型/工具调用、耗时、未知 usage 与中断消费范围。
- 同一题的修复前后证据，尤其列出原来通过、现在失败的任务。

当前所有 89 题都已被观察分析，不应称为未见测试集。以后若需要泛化结论，预先划定另一份未查看答案与轨迹的题集，并在方案冻结后使用。

## 指标与现实预期

| 指标 | 当前观察 | 下一阶段判定方式 |
|---|---|---|
| 最终全量通过 | 41/89（重评合并） | 独立完整运行另报；关注逐题净增与回退 |
| 明确启动 bug | portfolio-optimization | 离线与实际安装入口复现全部通过 |
| 已知权限误判 | 两种已复现模式 | 合法正例通过，真实危险负例仍受约束 |
| completed 却官方失败 | 7/26 | 同题对照减少，同时不过度增加未完成判定 |
| 验证故障 | 6 题，其中 2 无 reward | 原因可定位，依赖预检可用；不保证产物通过 |
| 预算耗尽 | 21 题，其中 3 通过 | 看无产物率、有效验证覆盖与成功成本，不能靠提早放弃降低超时数 |
| 契约冲突 | 48 个失败/未判分题中 25 次，涉及 12 题 | 正确恢复减少请求；保持原断言强度 |

不先设“修完必到 60%”之类无法支撑的承诺。最先能保证的是消除已复现的机制缺陷，能增加多少通过题由受控实验决定。

## 建议的实现拆分

第一批：入口隔离、权限分析修复、验收恢复接口，各自独立提交与验证。

第二批：验证环境/控制器可靠性、文件与服务交付检查。避免与算法提示策略混合，以便归因。

第三批：证据失效优化、工具反馈简化、阶段预算与独立语义验证。每项先有复现或对照，再决定是否保留。

当前只规划，不创建分支、不提交或推送、不启动任何评测。
